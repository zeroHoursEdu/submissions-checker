# Prometheus + Grafana observability — design

Date: 2026-09-15. Branch: `quiz-disputes-and-air-raid-pause` (new branch to be cut for this work).

## Goal

Replace the in-app analytics pages (DB-report HTML under `/teacher/analytics`) with
metrics scraped from the application and rendered in Grafana: a local Prometheus +
Grafana stack for development, and the already-hosted Grafana Cloud free tier for
production. Two dashboards: **Technical** (is the service healthy) and **Goals** (do
students use it). Telegram alerting when the service is not healthy.

Hard constraints from the owner:

- Existing Grafana Cloud dashboards (`komora-business`, `komora-observability`, the
  `GrafanaCloud` folder) are never touched. New assets live in their own folder.
- Free tier: stay far below 10k active series. Today 912 series are used by komora.
  Budget for this app: **under 500 series** in production (two replicas included).
- Only metrics with a clear question behind them. No per-student, per-subject,
  per-question, per-route-latency or GC series.

## Reference

The shape is copied from `silpoRestockAI`: the app exposes a Prometheus endpoint,
Grafana Alloy scrapes it and remote-writes outbound (no inbound port), dashboards are
generated by a Python script into committed JSON that both the local Grafana (file
provisioning) and Grafana Cloud (`make dashboards`, API push) render unchanged.

### Application side

- Dependency: `prometheus-client`.
- New package `src/submissions_checker/core/metrics.py`:
  - a module-level `REGISTRY` (a fresh `CollectorRegistry`, not the global default) so
    tests can assert on it and the GC collector is simply not registered.
    `ProcessCollector` and `PlatformCollector` are registered; `GCCollector` is not.
  - all metric objects (see catalogue) defined once here, imported by callers.
  - `app_info{revision}` set from `APP_REVISION` at import.
- `src/submissions_checker/core/metrics_middleware.py`: pure-ASGI middleware. Labels:
  - `route` = the matched route's path template (`request.scope["route"].path`);
    unmatched requests (404 on unknown path) are labelled `route="unmatched"` so bots
    scanning paths cannot create series. `/metrics` and `/static/*` are not counted.
  - `method`, `status_class` (`2xx`..`5xx`).
  - Duration histogram has **no route label**; buckets `0.05, 0.25, 1, 5, 15`.
- `GET /metrics` route in `api/routes/health.py`, returning
  `generate_latest(REGISTRY)` with the Prometheus content type. Unauthenticated: it is
  reachable only inside the compose network in production (Caddy answers 404 for the
  path) and on localhost in development.
- `src/submissions_checker/workers/scheduled/metrics_refresh.py`: scheduled job every
  60s (`METRICS_REFRESH_INTERVAL`, setting). Runs the gauge queries in one session and
  sets `app_db_healthy=1`; on any exception sets `app_db_healthy=0` and logs. Registered
  in `core/scheduler.py` next to the other jobs. Also runs once at startup after
  `init_db()` so a fresh replica does not report zero for a minute.
- Counters are incremented at the business event sites (route handlers and worker
  tasks). A counter increment never raises: metric names are fixed, labels are enum
  values, so no try/except wrapping is needed.

### Alloy

`observability/alloy/config.alloy`, one file for both environments, everything from env:

- `discovery.dns "app"`: names `[APP_METRICS_HOST]` (default `app`), type `A`, port
  `APP_METRICS_PORT` (default `8000`), refresh 15s. Docker's embedded DNS returns every
  replica's IP for a compose service name, so both replicas are scraped; locally the
  single `app` container resolves the same way.
- `prometheus.scrape`: `job="submissions-checker"`, interval 30s, path `/metrics`.
- `prometheus.remote_write`: `external_labels = {env = SUBCHK_ENV}`, endpoint
  `GRAFANA_CLOUD_PROM_URL` with basic auth `GRAFANA_CLOUD_PROM_USER/TOKEN`.
- Alloy's own `instance` label is `ip:port`; it changes on every deploy. Dashboards
  aggregate with `sum`/`max` so churn is invisible; the stale series drop out of the
  active count after Grafana Cloud's window.

### Compose

`docker-compose.yml` (local) gains three services under `profiles: ["observability"]`:
`prometheus` (`--web.enable-remote-write-receiver`, 24h retention, no scrape config),
`grafana` (anonymous Admin, file-provisioned datasource uid `grafanacloud-prom`,
dashboards from `observability/grafana/*.json`, alert rules from
`observability/grafana/alerting/`), `alloy` (same image tag as prod, env pointing at
local prometheus). Ports 9090, 3000, 12345.

`docker-compose.prod.yml` gains `alloy` under `profiles: ["observability"]`,
`mem_limit: 96m`, Watchtower label `false`, networks `[edge]` (needs outbound to Grafana
Cloud and reaches `app`, which is on `edge`). The memory budget comment is updated:
committed ~1636M, ~400M left for a sandbox. The profile is enabled by
`COMPOSE_PROFILES=observability` in the host `.env`, documented in `.env.prod.example`.

`docker/caddy/Caddyfile`: `@metrics path /metrics` → `respond 404` before the proxy.

### Grafana assets

```
observability/
  alloy/config.alloy
  grafana/
    build-dashboards.py      # writes the two JSON files; never hand-edit them
    subchk-technical.json
    subchk-goals.json
    alerting/
      build-alerting.py      # writes alert-rules.yaml (file provisioning format)
      alert-rules.yaml
    push.py                  # make dashboards / make alerting: API push to Grafana Cloud
  local/
    prometheus.yml
    grafana-datasource.yml
    grafana-dashboards.yml
```

- Dashboards: uids `subchk-technical`, `subchk-goals`; titles "Submissions Checker —
  Technical" / "Submissions Checker — Goals". Datasource by literal uid
  `grafanacloud-prom`. Queries filter `job="submissions-checker", env=~"prod|local"`.
- `push.py` creates (idempotently) the folder **"Submissions Checker"** (uid
  `subchk`) and upserts both dashboards into it. It never lists, edits or deletes
  anything outside that folder.
- Alerting: `push.py --alerting` upserts the Telegram contact point `subchk-telegram`,
  a notification policy route (`matchers: app=submissions-checker` → that contact
  point; the default policy is left as is), and the rule group `subchk` in folder
  `subchk`. Rules are generated by `build-alerting.py`, which also writes the
  file-provisioning YAML used by the local Grafana so both places carry the same rules.
- Makefile targets: `observability-up`, `observability-down`, `dashboards-json`,
  `dashboards` (push), `alerting` (push), `alloy-logs`.
- Env (`.env.example`, `.env.prod.example`): `GRAFANA_CLOUD_PROM_URL`,
  `GRAFANA_CLOUD_PROM_USER`, `GRAFANA_CLOUD_PROM_TOKEN`, `SUBCHK_ENV`;
  laptop-only: `GRAFANA_URL`, `GRAFANA_API_TOKEN`, `TELEGRAM_BOT_TOKEN`,
  `TELEGRAM_CHAT_ID`. Blank values mean "not pushed", never an error at app start.

## Metric catalogue

Series estimate assumes 2 replicas, ~45 route templates, ~1.4 methods per route, 2
status classes typical.

### Technical

| Metric | Type | Labels | Question it answers |
|---|---|---|---|
| `up` | scrape | instance | Is each replica reachable? (alert) |
| `app_info` | gauge=1 | revision | When did a deploy land? (annotation) |
| `http_requests_total` | counter | route, method, status_class | Which endpoint errors? Traffic. |
| `http_request_duration_seconds` | histogram (5 buckets) | — | p50/p95 latency |
| `http_requests_in_progress` | gauge | — | Are requests piling up? |
| `db_pool_checked_out`, `db_pool_size` | gauge | — | Pool exhaustion (pool 4+4 per replica) |
| `app_db_healthy` | gauge 0/1 | — | Can the app talk to Postgres? (alert) |
| `outbox_pending`, `outbox_error` | gauge | — | Is the queue draining? |
| `outbox_oldest_pending_age_seconds` | gauge | — | Is the queue stuck? (alert) |
| `outbox_processed_total` | counter | event_type, outcome | What fails in the background? |
| `check_duration_seconds` | histogram (5 buckets) | — | Is the sandbox slowing down? |
| `checks_total` | counter | outcome (passed/failed/error) | Are checks working? |
| `ai_reviews_total` | counter | outcome (ok/error/skipped) | Is the AI provider working? |
| `notifications_sent_total` | counter | outcome (sent/failed/skipped) | Is email working? |
| `process_resident_memory_bytes`, `process_cpu_seconds_total`, `process_open_fds` | default | — | 320m limit headroom |

### Goals

| Metric | Type | Labels | Question it answers |
|---|---|---|---|
| `students_total` | gauge | — | How many real students exist (REAL entity type) |
| `students_active` | gauge | window (1d/7d/30d) | How many distinct students logged in recently |
| `logins_total` | counter | role | Login pulse by role |
| `quiz_attempts_started_total` | counter | — | Quiz usage |
| `quiz_attempts_finished_total` | counter | status (COMPLETED/TIMED_OUT/VIOLATION_FAIL) | Completion vs failure mix |
| `quiz_attempts_in_progress` | gauge | — | Who is taking a quiz right now |
| `quiz_answers_total` | counter | — | Live activity pulse |
| `quiz_attempts_passed_total` | counter | — | Pass rate = passed / finished(COMPLETED) |
| `submissions_uploaded_total` | counter | — | Assignment usage |
| `submissions_awaiting_teacher_review` | gauge | — | Teacher backlog |
| `disputes_opened_total`, `disputes_resolved_total{status}` | counter | — / status | Are questions broken? |
| `disputes_open` | gauge | — | Teacher backlog |
| `air_raid_pauses_total` | counter | — | Feature used at all? |

Rough series count: http counter ~250, everything else ~120, process/platform ~30 —
about 400 with two replicas. Well under the 500 budget and 4% of the tier.

### Gauge refresh queries (one session, every 60s)

- `students_total`: `count(*) from students where type='REAL'`
- `students_active{window}`: `count(distinct u.student_id)` over `user_logins` joined to
  `users` for role STUDENT, `logged_in_at > now() - window`.
- `quiz_attempts_in_progress`: `count(*) from quiz_attempts where status='IN_PROGRESS'`
- `submissions_awaiting_teacher_review`: submissions with status `AWAITING_TEACHER_REVIEW`
- `disputes_open`: status `OPEN`
- `outbox_pending` / `outbox_error`: counts by state; `outbox_oldest_pending_age_seconds`:
  `now() - min(created_at)` over PENDING, 0 when none.
- `db_pool_*`: from the engine's pool, no query.

Test entities (EntityType.TEST) are excluded from the student counts.

## Dashboards

**Technical** rows: *Service* (up per instance, deploy revision, request rate,
5xx ratio, p50/p95, in-progress) · *Database* (`app_db_healthy`, pool checked-out vs
size) · *Background* (outbox pending/error/oldest age, processed rate by outcome,
check duration p95, checks by outcome, AI reviews by outcome, notifications by
outcome) · *Process* (RSS vs 320m limit, CPU).

**Goals** rows: *Students* (total, active 1d/7d/30d, logins per day by role) ·
*Quizzes* (in progress now, started/finished per day, finish status mix, pass rate,
answers per minute) · *Submissions* (uploaded per day, awaiting review backlog) ·
*Support* (disputes opened/resolved, open backlog, air-raid pauses).

Every panel description states the question it answers. Rates use `increase()` over the
dashboard range so replica restarts (counter resets) are handled by PromQL.

## Alerts

Grafana-managed rules, group `subchk`, folder `subchk`, evaluation every 1m, labels
`app=submissions-checker`, all routed to contact point `subchk-telegram`.

| Rule | Expression | For | No data |
|---|---|---|---|
| ServiceDown | `max(up{job="submissions-checker"}) < 1` | 3m | Alerting (Alloy or host died) |
| HighErrorRate | `sum(rate(http_requests_total{status_class="5xx"}[10m])) / sum(rate(http_requests_total[10m])) > 0.05 and sum(increase(http_requests_total[10m])) > 20` | 5m | OK |
| DbUnhealthy | `max(app_db_healthy{job="submissions-checker"}) == 0` | 2m | OK |
| OutboxStuck | `max(outbox_oldest_pending_age_seconds{job="submissions-checker"}) > 900` | 5m | OK |

Local Grafana provisions the same rules from `alert-rules.yaml` (no contact point, so
they only show state). The owner creates the Telegram bot with BotFather and puts the
token and chat id into the laptop `.env`; nothing in this design types a secret into a
browser form.

## Error handling

- Metric increments are infallible by construction (fixed names, enum labels).
- The refresh job catches everything, sets `app_db_healthy=0`, logs
  `metrics_refresh_failed`, and leaves the other gauges at their previous value.
- `/metrics` never touches the database.
- Alloy failing to push (bad token) is visible in `make alloy-logs`; the app is
  unaffected.
- `push.py` refuses to run without `GRAFANA_URL`/`GRAFANA_API_TOKEN` and prints where
  to get them; it aborts before any write if the folder uid `subchk` exists with a
  different title (someone else's folder).

## Testing

- Unit: middleware labels (template route, unmatched, static/metrics excluded, status
  classes); `REGISTRY` has no `python_gc_*`; refresh job sets gauges from a fake session
  and flips `app_db_healthy` on exception; `build-dashboards.py` output is valid JSON,
  uses uid `grafanacloud-prom`, contains no `${` / `$env` template variables, and every
  metric name referenced in a query is registered in `core/metrics.py`; the same
  registered-name check for `build-alerting.py`.
- Functional (real app + Postgres): `GET /metrics` returns 200 with
  `http_requests_total` and `students_total`; a login increments `logins_total{role}`;
  starting a quiz increments `quiz_attempts_started_total`; `/metrics` is not counted
  in `http_requests_total`.
- Manual verification, recorded in the PR: `make observability-up`, local Grafana shows
  both dashboards with data; `make dashboards` and `make alerting` against Grafana Cloud
  create the folder and rules; komora dashboards untouched (confirmed via the API
  listing before and after); a Telegram test notification arrives.

## Out of scope

Logs and traces to Grafana Cloud; per-subject drill-downs; a public dashboard link;
replacing the teacher-facing pages with embedded Grafana panels.
