## 5. E2e test fixture: seed `e2e_test` via real upload

- [x] 5.1 **Revised on investigation:** `tests/e2e/steps/subject_steps.py`'s `ensure_subject_exists` already registers the `e2e_test` subject via a real ZIP upload (`tests/e2e/fixtures/sample_subject.zip`, a deliberately minimal, camera-free fixture distinct from `plugins/e2e_test/`) — it never depended on the startup scan at all, since the e2e compose's `PLUGINS_DIR` was already a host-absolute path unreachable from inside the app-e2e container, making the scan a no-op there even before this change. No fixture-seeding change was needed. (An initial attempt to instead zip the real `plugins/e2e_test/` directory — which carries full camera/anti-cheat config never exercised by any e2e scenario — was reverted after it broke quiz tests by requiring webcam permission the test browser never grants.)
- [x] 5.2 **Real bug found and fixed instead:** removing the startup scan makes `ensure_subject_exists`'s upload branch the guaranteed-first-invocation path (previously masked whenever the e2e Postgres volume happened to already have the subject from an earlier run). This exposed a latent bug: the step assumed a fresh, unauthenticated page, but `analytics.feature`'s Background logs in as admin first, so navigating to `/auth/login` while already authenticated skips the login form and the subsequent `page.fill("#username")` times out. Fixed by adding `lp.logout()` before `lp.navigate()`/`lp.login()` in `ensure_subject_exists`.
- [x] 5.3 Ran the e2e suite repeatedly (fresh-volume `docker compose down -v` + `up --build --wait`, both full `tests/e2e/` runs and focused subsets) across many iterations while diagnosing the above. Quiz, submission, security, and the new anti-cheat keyboard-shortcut e2e tests passed consistently, including in full 35-test runs. Two narrow flakes surfaced only under aggressive fresh-volume resets and did not reproduce in smaller/warmer runs: (1) `test_admin_views_analytics_dashboard_without_errors` occasionally still fails on a cold-started stack's very first request even after the logout fix, and (2) `test_student_submits_work_that_fails_the_check` occasionally exceeds its submission-wait timeout under heavy concurrent Docker load (this session ran many consecutive stack rebuilds). Neither traces to `main.py`'s scan removal or `config_apply.py`'s extraction logic — both sit in test-infra/timing territory (login-page cold start, sandbox-check wall-clock under load) orthogonal to this diff. Documenting as known, unresolved flakes rather than blocking on them further.
